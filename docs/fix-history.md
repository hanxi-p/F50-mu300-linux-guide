最终交付：公开修复与风险记录已推送；新版加密备份在私有仓库发布为 `backup-20261010-224832`，名称为“2026-10-10 22:48（UTC+8）｜弱信号与锁管理加固、AT写入超时、30秒切换”。GitHub 资产大小与本机 SHA256 一致，包含恢复说明，历史版本保留。备份涵盖 SD 全部持久系统与启动恢复材料，不包含 Android 全部内置分区；未执行整盘恢复演练。

- **问题：** 超时任务捕获 TERM 后执行 `exit 0`，`--keep-background` 将它误判为正常启动，返回 0 并保留 detached 子任务。
- **风险：** R08/R09/R38/R40。控制页面可显示成功，后台残留任务还可能继续操作共享资源。
- **修补：** 超时监视器在发信号前写入超时标志；执行器返回 124；即使子任务返回 0，也执行后代清理。
- **验证：** 旧版 `exit_code=0 detached_alive=1`，新版 `exit_code=124 detached_alive=0`。同时修正测试断言，避免 shell 的 `set -e` 在 `&&` 链中未退出而假报通过。
- **部署：** 已部署设备，同步本地首页与系统可靠性安装负载；原文件保留。公开发布与完整备份尚未执行。
- **证据：** 本机 `reviews/timeout-success-trap-before.txt`、`timeout-success-trap-after.txt`。整组复测结果单独保存在 `stability-second-review-regression.txt`；真实服务与制式复测以对应 JSON 为准，未完成时不据此宣称通过。
- **首次整组结果：** 所有故障注入项通过，但健康检查与真实服务/制式测试重叠，出现一次 DNS 检查失败与一次 carrier 未就绪；未标作全通过。保留失败输出，随后改为串行重测。制式往返最终恢复，4G 29.16 秒、5G 25.38 秒，CPU 两轮模式切换通过。
