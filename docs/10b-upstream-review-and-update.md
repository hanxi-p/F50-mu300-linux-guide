# 已安装设备：上游修正与更新步骤

本页适用于已经正常运行 OpenWrt 的 F50。先识别当前系统和自定义改动，再决定需要更新哪一部分；沿用当前管理地址、无线、性能模式和加速配置。新设备安装仍从[全流程入口](10-codex-runbook.md)开始。

## 已验收的现有设备维护范围（2026-10-28补充）

保留v2026.10.11 rootfs，使用官方v2026.10.27.2的5.4内核/模块底座，源码重建无线模块保留ARP/DNS保护及EDMA回压处理。双向传输、真实重启与日志验收见[维护检查](reviews/2026-10-28-maintenance-acceptance.md)及[扩展仓库源码修复记录](https://github.com/hanxi-p/F50-OpenWrt-Dashboard/blob/main/docs/reviews/2026-10-28-edma-source-repair.md)。这不代表整包OpenWrt25.12.6、所有面板或其他设备均已通过。

已有定制设备优先差异部署，不运行旧整包稳定性安装器覆盖新组件；前端、通知、归属映射和私有名单分别保留。更新后重新备份当前文件，旧基线完整备份仍保留，两者都标明范围。新增通知与设备归属的源码在扩展仓库维护，不复制到首次刷机主线。

## 3. 只读识别当前状态

在设备 SSH / 串口执行，输出保存在本机私有工作目录：

```sh
date
cat /proc/sys/kernel/random/boot_id
cat /proc/uptime
cat /etc/mu300/image-version
cat /etc/openwrt_release
uname -r
mount
df -h
mu300-next-boot status
mu300-update --help
ip link show
ubus call network.interface.wan status
uci -q get firewall.@defaults[0].flow_offloading
uci -q get firewall.@defaults[0].flow_offloading_hw
logread | tail -n 100
dmesg | tail -n 100
```

再根据实际接口检查 AP、USB 管理、蜂窝上游和现用无线模块的路径 / SHA256。使用设备实际枚举出的名称，不照搬其他路由器的接口或模块。记录是否已有本地驱动修补、第三方面板、短信、代理、DNS 和登录修改；缺失的命令或查询失败单独记录，不据此写入默认配置。

## 4. 修改前备份与保留清单

按[完整备份](07-backup-and-restore.md)保存 SD 持久系统、当前启动镜像、匹配模块、启动控制信息及恢复入口，复制到电脑并验证归档和 SHA256。备份不能只留在将要更新的同一张卡上；更新后保留更新前备份，再制作新版备份。

| 保留对象 | 检查方式 |
|---|---|
| 网络、无线、防火墙、性能与加速设置 | 私有保存配置及哈希，更新后逐项比较；既有设备不重新套用教程中的示例 SSID、地址或 balanced 模式 |
| SSH 密钥、密码、会话与免登录设置 | 保存现用配置及修改过的认证文件；比较新版 dispatcher 接口后迁移定制，避免覆盖修复或添加新的免登录设备 |
| 自定义面板、RPC / ACL、采集服务 | 保存安装清单、活动 JS 版本及文件哈希；上游同名文件逐项合并，不能整包覆盖新版 LuCI |
| 设备流量 | 使用该功能时保存 `/etc/f50-devices/ledger.json`、`aliases.json`，并记录本地日期、累计值和采样状态 |
| 套餐 / 月度历史、vnStat、短信与扩展 | 按现用服务定位持久数据和配置，更新前后比较；订阅、SMTP、密钥和设备名单只保存在私有材料 |

有后台写入的数据按服务提供的快照 / 停写方法复制并恢复原服务状态。不能可靠迁移的字段保留原始副本并列明缺失范围，不清零有效历史、不虚构补齐。新系统首次采样重新建立速率基线，旧累计值不能作为当前字节增量再次计入。

## 5. 选择更新范围，再执行匹配步骤

1. **仅排查日志或界面问题：** 先做差异和健康检查，修复对应组件。无需降级、解锁、格式化 SD，也不自动整系统升级。
2. **需要上游 5.4 无线修复：** 核对目标发行版的内核、完整配套模块、启动镜像生成方式、板型和回滚材料。现用 updater 支持什么参数，以其 `--help` 和对应固定源码为准；先审查 kernel / boot 更新路径如何获取目标资源、是否改写启动槽和保留旧模块。不要只替换一个同 vermagic 的 `.ko`，也不要为试用补丁切换至 6.x / 7.x。
3. **需要更新整个 OpenWrt：** 审查目标版本的文件迁移、冲突报告、软件包重装和回滚路径。新版 updater 声明会迁移用户改动，但这不能代替对自定义 LuCI / dispatcher 的兼容性审查。其默认 `apply` 范围可能包含所有已安装系统以及 kernel / boot，不能把裸 `apply` 当成单一面板更新。
4. **固定下载对象：** 从目标 release 获取资源与校验清单，按该发行版的发布密钥说明校验签名，再核对资源 SHA256。GitHub API digest 可用于交叉核对，不等同于签名验证。下载大包走电脑独立网络，再传到设备；不使用可变的 `latest` 代替已审查版本。
5. **完成具体执行方案：** 记录将写入的文件 / 分区、当前和目标版本、恢复命令、保留数据、管理重连方式及需要的重启。已获授权的范围继续执行；重启等尚未授权的动作，在方案与备份准备完成后说明影响并取得授权。

目标发行版 updater 支持 `MU300_RELEASE` 固定在线目标、`apply --from FILE|DIR` 使用离线资源、`report` 查看迁移结果，以及 `boot` 更新内核和启动镜像；这些是[目标版本源码](https://github.com/dikeckaan/mu300-linux/blob/fa7bd593c5da6bf7963164e5a274253c4705960f/rootfs/overlay/opt/mu300/bin/mu300-update)的能力，不代表设备旧版 updater 全部支持。不直接以新版脚本覆盖本指南旧的互斥修补；先比较其锁、超时、试启动和回退行为。保留回滚副本，不使用 `--no-rollback` / `clean` 来代替空间与备份规划。

下载阶段记录文件大小与 SHA256；源码构建还须确认补丁集与模块重新构建。Windows 传输 shell、JSON、无扩展脚本时保留 LF，既核对工作目录，也核对最终归档；不要用本地通过代替发布包通过。

## 6. 更新后的验收与回退

| 阶段 | 通过条件 |
|---|---|
| 写入后、重启前 | 安装退出状态正常；目标镜像 / 模块哈希对应；迁移报告、保留数据和回滚文件齐全；没有版本不符或空间不足告警 |
| 首次重启 | 运行内核、模块与目标一致；SD 根、默认启动和成功确认正常；AP、USB 管理、SSH、LuCI、蜂窝、DNS 与 HTTPS 恢复 |
| 实际传输 | 分别验证下载与上传、文件校验和以及空闲归零；重复至少三轮，记录实际持续时间、流量和错误增量；大流量测试依用户授权与套餐余量进行 |
| 错误日志 | 比较同一次启动的时间窗口和计数增量；区分正常 IPA 恢复、驱动拒发、队列卡住、OOM、oops、MMC / EXT4 错误及异常模块加载请求；日志静音不能单独判为通过 |
| 自定义功能 | 面板与认证逻辑正常；实时采集不因刷新重复累计；名称映射和有效累计保留；实际测试重启、跨日 / 跨月、接口切换，未执行的单列为未测 |
| 长期运行 | 延长弱信号、重连、温度 / CPU 和加速场景观察；短时传输通过不代表运营商计费级精度或长期稳定性已验证 |

历史 `tx_errors` 累计值不必清零；以更新后的新增错误、队列恢复与真实通信判断。真实传输失败或管理功能回归时，按预先核对的系统 / 启动回退路径恢复，内核与模块成套恢复。回退还需保护更新后的有效流量和短信，不能直接用旧数据覆盖新数据。AP 自动回退只覆盖其实现检查到的启动失败，不是所有故障的恢复保障。

最后记录三层结果：语法 / 文件一致性、更新与回退逻辑、实际场景测试，分别标注通过、失败、未测或不适用。仅通过文档审查时，不宣称设备已升级；全部相关检查完成后，再更新已验证基线与安装步骤。

## 2026-10-29 追加维护：EDMA数据门控与节点通知

官方底座的回压重试之后，仍须检查数据到达唤醒是否绕过等待。可选社区源码补丁仅为数据增加门控、完成唤醒及20毫秒兜底，不扩大队列或关闭日志。通过范围及剩余回压/充电警告见[追加维护](reviews/2026-10-29-edma-route-maintenance.md)；它不改变本页的首次安装基线或整包rootfs验收结论。主线路节点变化可另选双渠道通知，凭据和实际配置仅保存私有材料。
