# 第十一章：基于原版的报错修复与驱动定制优化

本章用于已经安装 OpenWrt 的 F50。完成[第十章](10a-post-install-optimization.md)后，按实际症状选择维护项目，记录原版与定制部分的差异；首次安装不要求套用全部补丁。遇到具体错误时，配合 [Q&A](08-troubleshooting.md) 和[上游修正与更新](10b-upstream-review-and-update.md)处理。

我们是在上游和厂商已有源码上打补丁、重新编译无线模块，并修正面板与后台服务。无线驱动、用户态服务和页面属于不同层，分别记录修改与验收。

## 11.1 原版、官方维护与定制部分

| 层级 | 已核对的组合 | 维护范围 |
| --- | --- | --- |
| 首次安装基线 | `v2026.10.11` / OpenWrt `25.12.5` | 保留既有 rootfs、用户配置、面板和有效历史 |
| 官方内核底座 | 官方 `v2026.10.27.2` 的厂商 5.4 内核及配套模块 | 已完成有限内核维护验收；不能据此认定整包新 rootfs 已通过 |
| 无线定制模块 | 匹配上述内核的 `sprd_wlan_combo.ko` | 从固定源码构建，叠加 AP ARP/DNS 和 EDMA 数据调度修补 |
| 面板与服务 | 本项目的面板、统计、登录依赖和辅助服务 | 按功能增量部署，具体源码在[面板与扩展仓库](https://github.com/hanxi-p/F50-OpenWrt-Dashboard)维护 |

官方 5.4 配套已经包含 EDMA 回压重试、完成回调唤醒、skb 头部、PCIe 描述符前缀及 IPv6 组播等修正。我们的追加补丁解决其后仍观察到的特定路径问题，不把社区构建称为官方原版模块。

版本与上游来源以 [versions.json](../versions.json) 和固定提交为准。这里记录的是已验收组合，不代表其他内核、板型或未来发行版可以直接使用同一个 `.ko`。

## 11.2 报错如何对应到修改

| 现象或报错 | 定位与修补 | 验收重点 |
| --- | --- | --- |
| AP 下 `CMD_TX_DATA` 拒绝发送 | 部分特殊报文走固件命令队列；在 PCIe AP/GO 模式让 ARP、普通 DNS 使用受流控的数据队列，保留其他模式及 DHCP、VoWiFi 分支 | ARP、A/AAAA 查询、实际双向传输和新增拒发日志 |
| `EDMA pending queue full`、`push link fail`、`tx return err` | 官方底座将满队列作为 `-EAGAIN` 回压处理，保留数据所有权与完成唤醒，避免消耗硬错误预算后误丢数据 | 队列继续前进、硬错误增量、文件校验和统计方向 |
| 队列满后仍被新数据反复唤醒 | 追加数据等待门控；完成通知立即恢复，20 毫秒期限及有界等待覆盖漏通知；控制命令继续优先处理 | 重复唤醒、完成竞争、超时兜底、退出和命令处理 |
| ARP / `special_data_flag` 常规日志频繁输出 | 将三处常规信息日志降为 debug，保留真实错误；不整体静音内核日志 | 原始错误仍能收集，传输正常，日志降噪与故障修复分别判断 |
| 无线启动默认命令返回 `-95` / `-12` | 仅对匹配的厂商驱动跳过不支持的默认天线、自动功率与距离 0 命令；显式参数保留 | AP 真正启动，显式设置失败仍能报告；不把命令 `-12` 等同 OOM killer |
| `f50devices factory yields invalid constructor`、登录 Cookie 的 `build_url` 未声明 | 修正 LuCI 模块构造器及 ucode 依赖、作用域等用户态问题 | 页面模块加载、登录保持及既有免密规则；这类错误不靠更换无线驱动处理 |

### EDMA 队列提示代表什么？

EDMA 是无线 PCIe 数据搬运路径的一部分，发送暂存队列保存等待提交的数据描述。生产端暂时快于硬件处理时，队列可能满，驱动应等待空间并重试。

`full, backpressure` 单独出现不等于发包失败。持续不前进、伴随 `push link fail` / `tx return err`、真实传输失败或接口错误增加，才需要继续定位。本次追加修补减少已知满队列期间的重复构建和提交，没有扩大队列或隐藏回压提示，也没有关闭硬件加速、温控或充电保护。

## 11.3 定制驱动的源码与构建顺序

在独立构建电脑上准备固定来源和匹配工具链，源码与许可见[无线源码修复目录](https://github.com/hanxi-p/F50-OpenWrt-Dashboard/tree/main/extras/dashboard/optional/wifi-source-repair)。已核对来源：

| 部分 | 固定提交 |
| --- | --- |
| mu300-linux 构建及官方补丁集 | `fa7bd593c5da6bf7963164e5a274253c4705960f` |
| 厂商 5.4 内核源码 | `b50db5b6224c11db42a246e8fcdaad1e1d59f478` |
| 无线模块源码 | `4381465ccaf87fcf3215b9cd42f4a685df40e5e0` |

1. 识别设备实际内核、模块、PCIe 无线与上游接口，对照目标发行包；不照搬其他路由器的接口名称。
2. 以匹配发行 Image 的配置和工具链准备构建环境，应用该固定版本的全部官方补丁。
3. 依次应用 `wlan_combo-zz-f50-ap-dns-arp.patch`、`wlan_combo-zzzz-f50-edma-wait.patch`，在独立源码副本构建无线模块。现有记录使用匹配的 Clang 12，保留 CFI。
4. 逐项比较内核配置、依赖、导入 CRC、导出和 CFI，记录产物 SHA256。已验收构建匹配 267 项导入 CRC 和 42 项导出；数量相同不能替代逐项匹配。
5. 先做隔离场景，再部署到匹配系统。重启后核对**实际已加载模块的 build ID**，不能仅凭磁盘文件已替换或 `vermagic` 相同认定新驱动已运行。

完整步骤见[构建说明](https://github.com/hanxi-p/F50-OpenWrt-Dashboard/blob/main/extras/dashboard/optional/wifi-source-repair/README.md)。公开仓库只提供源码和说明，设备使用的二进制、构建记录与恢复材料保存在私有目录。

## 11.4 部署、备份与回退

**准备什么：** 当前可用系统、原驱动及配置备份、已核对的新模块、独立管理连接和恢复资料。

- 更新内核底座时，内核与配套模块须一起核对、一起备份；旧 updater 的 `boot` 路径可能没有同步模块，不能只看 Image 写入成功。
- 已有底座匹配、只追加无线源码修补时，仅替换经过验证的无线模块，保留 rootfs、面板、认证、名称映射、短信和有效流量历史。
- 驱动正在使用时，磁盘替换不会立即改变运行中的模块。需要重载或重启时，说明 Wi-Fi/SSH 中断范围并安排操作时间；先备好 USB 或其他恢复通道。
- AP 试运行回退只覆盖系统已启动、检查能运行但 AP 未就绪的情况。原驱动、完整系统与启动恢复资料仍需保留，恢复入口见[备份与恢复](07-backup-and-restore.md)。

**完成标志：** 新旧产物与适用内核可追溯，备份可校验，实际加载版本已确认，管理和数据路径均通过检查。

## 11.5 配套的面板与后台优化

| 项目 | 定制内容与边界 |
| --- | --- |
| 设备流量 | 无线与USB共用一张在线表，整体可折叠并完整展开，离线设备另行折叠；按 MAC 保留原始采样基线，优先显示自定义名称；已确认私有 MAC 变化后合并展示。按实际 F50 上游拓扑核对外网流量，不重复累计各接口，也不为统计擅自关闭加速 |
| 统计显示 | 速率 B/s 使用整数，K/s、M/s、G/s 及流量 M/G 保留两位；显示舍入不改写账本或校准值 |
| DNS 与线路恢复 | 有界探测、连续失败确认、互斥与冷却；实际故障后换线，保持可用现用线路，周期检测不等于周期切换 |
| 通知 | 新短信和设备故障/恢复使用 Bark / WxPusher；节点变化仅发 Bark，接收后十分钟过期，解析实际节点并保留基线/编号去重。普通 WAN/DNS 中断不当设备故障，原短信邮件继续运行 |
| OpenClash 插件升级 | 先备份及simulate，保留custom、订阅与恢复钩子，重新适配DNS顺序；核对缺失自动任务字段默认值，插件和Mihomo核心分别管理。见[升级记录](https://github.com/hanxi-p/F50-OpenWrt-Dashboard/blob/main/docs/reviews/2026-10-29-openclash-upgrade.md) |
| 按需测速 | 快捷控制第二排三个测速按钮，蓝底／运行绿底，标题＋小字结果三行显示；再次点击复位，下一次重新测速；内网为当前终端与F50的HTTP双向吞吐，国内／国外分别测百度／谷歌的ping。虚拟IP不当真实ICMP，测试有大小／超时限制，不周期运行、不改加速；见[功能说明](https://github.com/hanxi-p/F50-OpenWrt-Dashboard/blob/main/docs/features/network-test.md) |
| 手机与宽屏面板 | 速率/流量上下排布、名称展示、表格对齐、触摸查看曲线和折叠入口分别适配；界面更新保留已有统计与滚动状态 |

按需选择[面板功能](https://github.com/hanxi-p/F50-OpenWrt-Dashboard#功能目录)，个人节点、免密设备、收件人和密钥只保存到私有配置。本章不把某台设备的配置作为所有 F50 的安装默认值。

## 11.6 已通过与尚未完成的验证

| 验证层级 | 已有记录 | 边界 |
| --- | --- | --- |
| 编译与兼容 | 配置、267 项导入 CRC、42 项导出及 CFI 匹配 | 仅对固定构建组合成立 |
| 隔离回归 | 14 个真实函数体场景，在 5.4 / 5.15 API 桩各三轮；新模块 ARM64 分类 776 项、EDMA 回压/完成 523 项各三轮 | 总线、IRQ、锁、固件及时钟有明确测试桩，不等于真实硬件验收 |
| 实机加载与传输 | 实际重启、加载 build ID 核对；三轮局域网每方向 64MiB、蜂窝每方向 2MiB，文件 SHA 一致，设备上下行统计方向正确 | 新设备按使用者流量预算安排小量蜂窝验证，不自动大流量测速 |
| 基础服务 | DNS、HTTPS、AP、流量采集、邮件及辅助服务检查通过 | 节点通知本轮未制造真实切换，不把隔离队列测试写成手机接收验收 |
| 长期与异常场景 | 尚未完成长期弱信号、持续重负载、异常掉电等验收 | 短时通过不能替代这些场景 |

当前仍可能出现 EDMA 回压提示；充电温度告警也保留待定位，没有写假温度或关闭保护。检查同一次启动的新增错误、实际通信与队列恢复，不要求清空历史错误计数来表示修复成功。

详细证据与历史失败见[官方底座/ARP/DNS 维护记录](https://github.com/hanxi-p/F50-OpenWrt-Dashboard/blob/main/docs/reviews/2026-10-28-edma-source-repair.md)、[EDMA 数据门控与节点通知记录](https://github.com/hanxi-p/F50-OpenWrt-Dashboard/blob/main/docs/reviews/2026-10-29-edma-and-route-notify.md)及[风险清单](risk-register.md)。
